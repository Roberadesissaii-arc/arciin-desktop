# Security architecture

How Arciin Desktop decides what to trust, where it keeps the one secret it
holds, and what the web view is allowed to do.

The governing idea: **the device credential is a native secret.** It is
obtained by Rust, stored by Windows, used by Rust, and never represented in
JavaScript, in a file, in a URL, or in a log line.

---

## 1. Discovery trust model

Anything that answers on a network address is untrusted input. A responder is
a candidate, never a server.

Two ways a candidate appears:

- **mDNS** (`_arciin._tcp.local.`) — a convenience. The server currently
  reports `advertised: false`, so this usually finds nothing. Every failure is
  swallowed; the user never sees an mDNS error.
- **A typed address** — always available, and the primary path in practice.

Neither is believed. Both go through the same verification below. Subnet
scanning is deliberately not implemented: probing addresses the user never
named is not something a connection client should do.

## 2. Manifest verification

`GET /.well-known/arciin`, then every one of these must hold
(`src-tauri/src/protocol.rs`):

| Check | Rejection |
| --- | --- |
| `service == "arciin"` | `NOT_ARCIIN` |
| `protocolVersion == 1` | `DEVICE_PROTOCOL_UNSUPPORTED` |
| `serverId` is a well-formed UUID | `INVALID_MANIFEST` |
| `instanceName` is non-empty | `INVALID_MANIFEST` |

The response body is size-capped (64 KB) so a hostile responder cannot stream
indefinitely, and redirects are not followed — a probe that bounces to another
host is not that host's manifest.

Error text from the server is **never** echoed to the user. Only the `code` is
read, and the message shown is this client's own copy. A spoofed endpoint
therefore cannot put chosen text on screen.

## 3. Server identity binding

This is the check that protects a LAN where addresses get reassigned.

```txt
yesterday   192.168.1.50  ->  serverId ABC   (paired, credential stored)
today       192.168.1.50  ->  serverId XYZ   (a different machine)
```

Before a stored credential is **read**, the manifest is fetched again and its
`serverId` compared to the expected one. A mismatch stops the connection with
`SERVER_ID_MISMATCH` and requires fresh pairing. The credential for ABC is
never offered to XYZ.

Credentials are keyed by `serverId`, not by address, so identity — not
location — is what selects a secret.

## 4. Pairing

A 6-digit PIN, generated by an owner or admin in Settings → Devices, claimed
once via `POST /api/devices/pair`.

- Sent in a JSON body. **Never** in a URL or query string.
- Never written to a log line.
- Server-side: Argon2id hashed, one-time, ~5 minutes, 5 attempts then locked,
  rate-limited per IP, claimed in a serializable transaction so exactly one
  client wins.
- Malformed input (not exactly six digits) is rejected client-side before a
  request is made, so typos do not consume attempts.

### Device metadata sent

Only what the protocol permits: `name`, `platform` (`windows`), `deviceType`
(`desktop`), `appVersion`, `protocolVersion`.

The device name defaults to the machine hostname, which Windows already
broadcasts on the LAN, and is editable before pairing.

**Not collected, and no code exists to collect them:** MAC address, Windows
product key, motherboard or disk serial, BIOS ID, or any hardware fingerprint.

## 5. Credential storage

The credential returned by pairing goes straight to **Windows Credential
Manager** through the `keyring` crate's native Windows backend.

| Property | Value |
| --- | --- |
| Store | Windows Credential Manager (generic credential) |
| Target | `arciin-desktop:device-credential:<serverId>` |
| Namespacing | per `serverId` — never one global key |
| Custom crypto | none; the OS store is the mechanism |

Explicitly never used: `localStorage`, `sessionStorage`, React state, any
store, JSON, SQLite, a config file, a log, a URL, a query parameter.

The interface is a trait (`CredentialStore`) with `save` / `load` / `delete`,
so a macOS Keychain backend can be added later without touching callers.

## 6. The IPC boundary

React can ask for a server to be paired or connected. It can never obtain the
thing that makes either work.

```txt
React  --(serverId, address, code)-->  Rust
                                        |
                                        +--> Arciin server
                                        |      returns credential
                                        +--> Windows Credential Manager
React  <--{ paired: true }-------------- Rust
```

There is **no command** that returns a credential and **no command** that
accepts one. The `PairResult` type carries `paired`, `serverId` and
`deviceName` — and has no field a secret could hide in. The raw credential is
never serialized across the Tauri IPC boundary.

## 7. Device authentication is not user authentication

```txt
Discovery   an Arciin server exists here
Pairing     this computer is an approved device
User login  a person is using that computer
```

A successful bootstrap means "this PC is trusted". It does **not** sign anyone
in. After the handover, the server's own login page appears and a human
authenticates normally. This client contains no login form and no session
logic of its own.

## 8. Device-to-WebView session bridge

The problem: Rust holds the credential, but the server recognises a trusted
device by an HttpOnly cookie on the **web origin**, which is where WebView2 —
not the Rust HTTP client — makes its requests.

The mechanism:

1. Rust reads the credential from Windows Credential Manager.
2. Rust calls `POST /api/devices/session` with
   `Authorization: Device <credential>`.
3. The server answers with its own
   `Set-Cookie: arciin_trusted_device=…; HttpOnly; SameSite=Lax; Path=/`.
4. Rust writes **that exact token** into WebView2's cookie jar via
   `ICoreWebView2_2::CookieManager`, preserving the server's attributes:
   `IsHttpOnly = true`, `SameSite = Lax`, `Secure` when the origin is HTTPS,
   and the server's own `expiresAt` (12 hours).
5. The Arciin window is then created and loads the origin — carrying the
   cookie on its very first request.

Why this is the secure option and not a workaround:

- The value transported is the **server's own short-lived session token**,
  byte for byte. Nothing is minted client-side and no new protocol is invented.
- It is written **HttpOnly**, so scripts on the Arciin page cannot read it —
  the same protection a browser would have given it.
- The **permanent credential never reaches the WebView** in any form.

What is never done: a token in a URL or query string
(`http://server/?deviceToken=…`), an injected script, `window.deviceCredential`,
`localStorage`, or any long-lived JavaScript-readable token.

Ordering detail: the cookie is installed through the onboarding window's
cookie manager *before* the Arciin window is created. WebView2 shares one
cookie jar across the app's profile, so this guarantees the first request is
already trusted rather than an untrusted load followed by a reload.

## 9. WebView origin restriction

The Arciin window is pinned to the connected server's origin by an
`on_navigation` guard:

| Target | Result |
| --- | --- |
| Same origin (scheme + host + port) | allowed |
| Another `http`/`https` origin | blocked; handed to the system browser |
| `javascript:`, `data:`, `file:`, anything else | blocked; nothing opened |

Comparison uses `Url::origin()`, so `https://arciin.example.com.evil.test`
does not pass as `https://arciin.example.com`. Tests cover exactly that case.

The Arciin window is also **absent from the capability allowlist**
(`src-tauri/capabilities/default.json` lists only `main`), so pages served by
the remote origin have no access to any Tauri command — not even the ones the
onboarding UI uses.

## 10. Revocation

When the server reports `DEVICE_REVOKED` or `DEVICE_INVALID`:

1. Retrying stops immediately.
2. The credential **for that server only** is deleted from Windows Credential
   Manager.
3. The saved server is flagged `revoked` so the UI can explain rather than
   silently fail, offering **Pair Again**.
4. Other servers' credentials are untouched.

## 11. Forget server

A local action: deletes the saved metadata, deletes the OS credential for that
`serverId`, and clears the WebView cookies for that origin.

It does **not** revoke the device server-side. Server-side revocation stays an
owner/admin action in Settings → Devices, and the UI says so.

## 12. TLS

- Certificate validation is **never** disabled. The equivalent of
  `danger_accept_invalid_certs(true)` appears nowhere in this crate.
- Plain HTTP is supported because an unencrypted trusted LAN is a valid Arciin
  deployment.
- An explicit `https://` address is **never** silently downgraded to `http://`.
  A bare LAN address defaults to `http://`; a bare public hostname is tried
  over `https://` first.
- Self-signed certificates are not supported in V1 (see README limitations).

## 13. Timeouts

Every native request is bounded, so no UI state can hang:

| Operation | Timeout |
| --- | --- |
| Connect (all requests) | 5s |
| Discovery manifest | 6s |
| mDNS browse window | 4s |
| Device bootstrap | 15s |
| Pairing claim | 20s (server-side Argon2id) |
| WebView bridge handover | 10s |

## 14. Logging policy

Logging is enabled with `ARCIIN_LOG` and is deliberately shape-only.

**Logged:** host/origin, `serverId`, `deviceId`, protocol version, connection
stage, elapsed time, error code.

**Never passed to a logging macro anywhere in this crate:** the pairing PIN,
the device credential, the session cookie value, any password, the
`Authorization` header, or a licence token.

Transport errors are classified into a code rather than printed, because a
`reqwest` error string can contain the full request URL.
